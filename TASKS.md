# Детальные планы

## T-051. Вход через соцсети и ЕСИА

**Статус:** ЗАВЕДЕНА

README: «регистрация пользователя в системе (в том числе через социальные сети,
ЕСИА, маркетплейсы?)». Не реализовано.

**План**
1. Решается вместе с T-041: если остаётся Keycloak — внешние провайдеры
   настраиваются в нём (identity brokering) и своего кода почти не требуют.
   Это сильный аргумент в пользу Keycloak, и его нужно учесть в ADR.
2. Модель связывания: один локальный пользователь — несколько внешних
   идентичностей; таблица `user_identities (provider, external_id, user_id)`.
3. Обработка коллизий: внешний аккаунт с почтой уже существующего пользователя
   не должен молча захватывать чужой профиль.
4. ЕСИА требует регистрации информационной системы и работы с УКЭП —
   зафиксировать в требованиях как внешнее ограничение, а не как код.
5. Маркетплейсы как провайдер входа: проверить, отдают ли OZON и WB OAuth
   для сторонних приложений; если нет — убрать пункт из требований
   (в README он и так помечен вопросом).

**Проверка:** вход через одного внешнего провайдера сквозным сценарием.

## T-052. Сервис списка желаний

**Статус:** ЗАВЕДЕНА

Восемь требований README, не реализовано ничего. Это ядро продукта.

**План**
1. Новый сервис `wish` со своей схемой.
2. Модель: список желаний пользователя, элемент списка, приоритет,
   ссылка на товар маркетплейса (T-057) либо денежная сумма.
3. Статусная модель элемента строго по README: `виден`, `не виден`, `выбран`,
   `подтверждён`, `акцептован`, `отклонён`. Переходы — явной таблицей,
   недопустимый переход — ошибка, а не молчаливое присвоение.
4. Резервирование: выбранный элемент не виден другим дарителям. Резерв
   с таймаутом, иначе брошенные резервы навсегда блокируют подарок.
5. Уведомление одаряемого о намерении подарить, подтверждение или отклонение
   (через T-059).
6. Денежный элемент списка — перевод через кошелёк (T-043) или СБП (T-058)
   с комиссией.
7. Конкурентный доступ: два дарителя не должны зарезервировать один элемент.
   Блокировка на уровне БД, тест на гонку.
8. Права: чужой список виден только в части элементов со статусом «виден».

**Проверка:** сквозной сценарий даритель → резерв → подтверждение → акцепт;
тест на параллельное резервирование.

## T-053. Сервис котла: базовый жизненный цикл

**Статус:** ЗАВЕДЕНА

Восемь требований README, не реализовано ничего. Котёл дал название проекту.

**План**
1. Новый сервис `caldron` со своей схемой; типы котла заложить с самого начала
   (общая часть + специфика), чтобы T-054 и T-055 не переписывали модель.
2. Модель: котёл, участник, взнос, тип, состояние.
3. Состояния: `подготовка` → `готов` → `завершён`, плюс `отменён` из любого.
4. Добавление участников — только создателем и только в состоянии `подготовка`.
5. Сумма взноса: фиксированная, индивидуальная или диапазон.
6. Переход в `готов` — только когда все участники внесли средства.
   Проверка суммы против кошелька (T-043), а не на слово.
7. Отмена: возврат средств всем внёсшим. Возврат обязан быть транзакционным
   и идемпотентным — это денежная операция, повтор при сбое не должен
   вернуть дважды.
8. Роль создателя: участник или арбитр — разные виды котла.
9. Уведомления участникам о добавлении и о смене статуса (T-059).

**Проверка:** сценарии сбора и отмены; сумма средств в системе до и после
отмены совпадает.

## T-054. Котёл подарков

**Статус:** ЗАВЕДЕНА

Четыре требования README. Зависит от T-052 (списки), T-053 (котёл), T-043 (кошелёк).

**План**
1. Каждый участник формирует список из 5 подарков, суммарная цена которых
   не превышает общую сумму котла — проверка на момент подтверждения
   и повторно на момент розыгрыша: цены на маркетплейсе меняются.
2. Запуск розыгрыша создателем или назначенным арбитром.
3. Генератор случайных чисел — только `crypto/rand`. `math/rand` в розыгрыше
   с деньгами недопустим: последовательность предсказуема.
4. Розыгрыш проверяемый: сохранять seed/commitment до розыгрыша и раскрывать
   после, чтобы участник мог убедиться в честности. Без этого механизм
   не отличим от произвольного выбора организатором.
5. Второй розыгрыш — выбор набора подарков победителя из его списка
   в пределах суммы котла; остаток переводится на карту или в кошелёк
   (пример из README: 3400 + 1600 + 5000 при котле 10000).
6. Заказ выбранных подарков через маркетплейс (T-057).
7. Результат розыгрыша неизменяем и хранится в истории.

**Проверка:** воспроизводимый тест розыгрыша с фиксированным источником
случайности; проверка ограничения по сумме.

## T-076. Адаптеры маркетплейсов OZON и WB

**Статус:** ЗАВЕДЕНА (нужен доступ к API)

Выделено из T-057. Контракт, кэширование, размыкатель цепи и заглушка
реализованы, решение записано в [ADR 0004](docs/adr/0004-marketplace-integration.md).
Осталось то, что нельзя сделать без доступа к API площадок.

**Что нужно выяснить до кода**

Публичные API OZON и WB ориентированы на продавца. Оформление заказа
от имени произвольного покупателя в них не предусмотрено. Пока не
подтверждено обратное, требование FR-24 «выбранный подарок заказывается
автоматически» может быть невыполнимым — и тогда переписывать нужно
требование, а не код.

**План**
1. Получить доступ к API хотя бы одной площадки и выяснить фактические
   возможности: карточка товара, цена, наличие, оформление заказа.
2. Рассмотреть партнёрские программы как основной источник карточек:
   они дают ссылки и данные о товаре, но заказ — вряд ли.
3. Реализовать адаптер, возвращающий `ErrUnsupported` для недоступных
   операций, а не имитирующий их.
4. Ключи API — в секретах, не в репозитории.
5. Учесть ограничения частоты: значения кэша подобрать под реальные лимиты,
   а не наугад.
6. Если оформление заказа недоступно — переписать FR-24 на сценарий
   со ссылкой и ручным заказом дарителем.

**Проверка:** карточка реального товара читается, а недоступные операции
честно возвращают `ErrUnsupported`.

## T-058. Платёжный контур: СБП и вывод средств

**Статус:** ЗАВЕДЕНА

README: СБП для перевода напрямую пользователю или в систему, вывод средств,
привязка карт МИР. Не реализовано; кошелёк (T-043) закрывает только внутренние
операции.

**План**
1. Выбор провайдера и юридические ограничения зафиксировать до кода: приём
   и вывод денежных средств требует статуса или договора с платёжным агентом.
   Для учебного проекта — работать с песочницей провайдера и записать
   ограничение в требования (T-045).
2. Интерфейс платёжного провайдера: пополнение, выплата, статус операции.
3. Вебхуки о статусе платежа: проверка подписи, идемпотентность по идентификатору
   события, устойчивость к повторам и переупорядочиванию.
4. Сверка: локальный статус операции против статуса у провайдера,
   регулярная выверка расхождений.
5. Привязка карт: хранить только токен провайдера. Номера карт в системе
   не появляются ни в каком виде, включая логи.
6. Комиссия при переводе денежного подарка — правило вынести в конфигурацию.
7. Денежные операции — только с ключом идемпотентности (механизм готов
   в кошельке, T-043).
8. Circuit breaker на вызовы провайдера: его недоступность не должна
   ронять запрос целиком.

**Проверка:** песочница провайдера, повторная доставка вебхука не создаёт
второй платёж.

## T-066. Веб-интерфейс на Go WebAssembly

**Статус:** ЗАВЕДЕНА

У системы нет пользовательского интерфейса вообще. Единственная страница —
форма входа в собственном OAuth2-провайдере (T-061), и та отдаётся
серверным шаблоном. Проверить работу списка желаний, котла или кошелька
можно только через `curl` и коллекции в `_requests`.

Интерфейс на Go WebAssembly позволяет держать весь код на одном языке
и переиспользовать модели из `services/shared`, что для учебной цели №1
из README («писать на Go») даёт больше, чем отдельный фронтенд на JS.

**План**

1. **Проработка до кода.** Решение оформить как ADR: WASM даёт единый язык
   и общие модели, но платит за это размером бандла (даже с `tinygo` это
   сотни килобайт против десятков у JS), отсутствием SSR и слабой
   экосистемой UI-компонентов. Зафиксировать, что именно перевешивает.
2. **Выбор подхода:** `syscall/js` вручную, либо фреймворк
   (`vugu`, `go-app`, `vecty`). Критерии: живость проекта, размер бандла,
   отладка. Не перечислять варианты в отчёте — выбрать один и обосновать.
3. **Сборка:** `GOOS=js GOARCH=wasm`, `wasm_exec.js` из дистрибутива Go,
   отдельная цель в `Makefile` (T-029) и шаг в CI (T-030).
   Проверить, оправдывает ли `tinygo` усложнение сборки.
4. **Раздача статики:** отдельный сервис или nginx в compose; маршрут
   на шлюзе. Не подмешивать статику к API-сервисам.
5. **Аутентификация из браузера:** Authorization Code Flow с PKCE
   (T-061 уже реализован). Токен не хранить в `localStorage` — он доступен
   любому скрипту на странице; либо httpOnly-cookie, либо только в памяти
   с молчаливым обновлением.
6. **CORS:** сейчас `allow_origins` сужен до localhost (T-001), origin
   интерфейса нужно будет добавить явно.
7. **Экраны первой очереди:** вход, профиль (T-050), кошелёк (T-043),
   список желаний (T-052). Остальное — по мере появления сервисов.
8. **Переиспользование моделей:** типы из `services/shared` компилируются
   и под `js/wasm`, но `database/sql` и драйверы — нет. Проверить, что
   общие пакеты не тянут серверные зависимости, иначе их придётся разделять.

**Зависит от:** T-050, T-043, T-052 — до появления самих сервисов
показывать в интерфейсе почти нечего. Разумно начать с ADR и каркаса
сборки, а экраны добавлять вслед за сервисами.

**Проверка:** страница открывается через шлюз, проходит вход по PKCE
и показывает данные профиля, полученные из API.

## T-072. Доставка в окружения

их некуда: целевого окружения не существует. Пока его нет, обсуждать

**План**

3. Миграции в процессе доставки: сейчас их применяет сам сервис при старте,
   и несколько инстансов конкурируют за блокировку. Решить, выносить ли их

4. Стратегия выката и откат: что откатывается — образ, схема, оба.
   Откат миграции возможен не всегда, пример уже есть в T-024.
5. Проверка после выката: health-эндпоинты и дымовой сценарий.
6. Защита ветки `main` и обязательное прохождение CI перед слиянием.

**Проверка:** выкат и откат опробованы на staging.

## T-073. Срок хранения истории транзакций и архивация партиций

**Статус:** ЗАВЕДЕНА

Выделено из T-067. Партиции транзакций теперь создаются автоматически
вперёд, но назад не убираются: таблица растёт бесконечно, просто
по месячным кускам.

Решать это без ответа на вопрос «сколько лет хранится история операций»
нельзя, а такого требования в проекте нет — нефункциональные требования
вообще не зафиксированы (T-045).

**План**
1. Зафиксировать срок хранения в реестре требований (T-045). Для денежных
   операций он обычно определяется не удобством, а регуляторными
   требованиями — это нужно проверить, а не придумать.
2. Отсоединение старых партиций (`DETACH PARTITION`) вместо удаления:
   отсоединённая таблица остаётся доступной для выгрузки.
3. Выгрузка в холодное хранилище и только затем удаление.
4. Метрика: возраст самой старой партиции.
5. Учесть в модели угроз (T-046): удаление финансовой истории — операция,
   которую нельзя отменить, и права на неё должны быть отдельными.

**Проверка:** партиция старше срока хранения отсоединяется, данные
остаются доступны для выгрузки.

## T-075. Подтверждение телефона и почты

**Статус:** ЗАВЕДЕНА

Выделено из T-050. Телефон обязателен при регистрации, но обязательность
формы — это ещё не подтверждение: пользователь может ввести чужой или
несуществующий номер. Поле `phone_confirmed` заведено и сбрасывается
при смене номера, но подтверждать его нечем.

Пока номер не подтверждён, полагаться на него нельзя: ни для восстановления
доступа, ни для оповещений (T-059), ни как на признак живого пользователя.

**План**
1. Код подтверждения с ограниченным сроком жизни и числом попыток;
   хранить хеш кода, а не сам код.
2. Ограничение частоты отправки: без него эндпоинт отправки превращается
   в средство рассылки за чужой счёт.
3. Канал доставки — тот же сервис оповещений (T-059).
4. Подтверждение почты по ссылке с одноразовым токеном.
5. Решить, что делать с неподтверждёнными: срок на подтверждение
   и последствия его истечения.
6. Ужесточить схему: `phone NOT NULL` после дозаполнения существующих
   записей (сейчас колонка nullable именно поэтому).

**Проверка:** неподтверждённый номер нельзя использовать для восстановления
доступа; повторная отправка кода ограничена по частоте.
