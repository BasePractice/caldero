## T-003. Починить сломанные SQL-запросы в `users`

**Статус:** ЗАВЕДЕНА

Три независимых дефекта, из-за которых OAuth2-провайдер нерабочий:

1. [db.go:100](services/cmd/users/db.go:100) — `WHERE id = $1`, колонки `id`
   в таблице `keys` нет, есть `key_id`. Подпись токенов невозможна.
2. [db.go:117-124](services/cmd/users/db.go:117) — `rowid` в PostgreSQL не существует.
   `ClearKeys` всегда падает, `RotateKeys` возвращает ошибку.
3. [db.go:257-262](services/cmd/users/db.go:257) — `signature = ? AND token_type = $1`:
   смешаны стили плейсхолдеров, один плейсхолдер на два аргумента, порядок перепутан.

**План**
1. `GetKey`: `WHERE key_id = $1`.
2. `ClearKeys`: удалять по `key_id NOT IN (SELECT key_id ... ORDER BY created_at DESC LIMIT 2)`.
3. `deleteTokenSession`: `WHERE signature = $1 AND token_type = $2`.
4. Пройти остальные запросы файла на тот же класс ошибок.
5. Завести задачу на интеграционный тест, который ловил бы такое (см. T-034).

**Проверка:** `go build ./...`; ручной прогон запросов против поднятого PostgreSQL.

## T-008. Fail-fast вместо `nil` из конструкторов

**Статус:** ЗАВЕДЕНА

`NewDatabaseUsers`, `NewDatabase` (credit, account), `NewDatabaseWallet` при ошибке
возвращают `nil` интерфейса. Сервис стартует и падает с nil-разыменованием на первом
запросе. `NewKeyManager` вызывается как `keyManager, _ :=`
([service.go:40](services/cmd/users/service.go:40)) — ошибка теряется полностью.

**План**
1. Все `New*` возвращают `(T, error)` с оборачиванием через `%w`.
2. `newService` тоже возвращает ошибку.
3. В `main` ошибка старта — единственное место, где допустим `panic`
   (по `RULE.md`); лучше `slog.Error` + `os.Exit(1)`.
4. Аналогично `NewDefaultCache` в [wallet/main.go:48](services/cmd/wallet/main.go:48).

**Проверка:** старт без БД завершается с кодом 1 и внятным сообщением, а не позже.

## T-016. Единый bootstrap сервиса + graceful shutdown

**Статус:** ЗАВЕДЕНА

Четыре `main.go` совпадают почти дословно, и в каждом продублированы одни и те же
дефекты. [services/exit.go:11-19](services/exit.go:11) возвращает
`context.Background()` — контекст, который никогда не отменяется, поэтому отмена
по сигналу до обработчиков не доходит, а `os.Exit(0)` рвёт активные запросы.

**План**
1. `services.Run(name string, run func(ctx context.Context) error) ` — общая точка входа:
   конфигурация, логирование, метрики, сигнальный контекст, код возврата.
2. `signal.NotifyContext` с возвратом производного контекста; `defer cancel()`.
3. HTTP: `srv.Shutdown(ctx)` с таймаутом; gRPC: `GracefulStop()` с таймаутом
   и `Stop()` по его истечении.
4. Закрытие пула БД и Redis после остановки сервера.
5. Удалить `exit.go` и `recover()` в `main` — он не ловит паники обработчиков
   и создаёт ложное ощущение защищённости. Вместо него — recover-middleware
   на mux и `grpc_recovery` интерсептор.

**Проверка:** SIGTERM во время долгого запроса — запрос завершается, процесс выходит с 0.

## T-018. Таймауты `http.Server`, ограничение размера тела запроса

**Статус:** ЗАВЕДЕНА

Все три HTTP-сервиса используют `http.ListenAndServe` без таймаутов (Slowloris),
`json.NewDecoder(r.Body)` читает неограниченный объём.

**План**
1. Явный `&http.Server{ReadHeaderTimeout, ReadTimeout, WriteTimeout, IdleTimeout}`.
2. `http.MaxBytesReader` на теле запроса.
3. `decoder.DisallowUnknownFields()` — опечатка в поле должна быть ошибкой,

   Аргумент за переезд — `lib/pq` в режиме поддержки, `pgx` даёт
   `COPY`, слушателей и нормальные типы.
2. Решение по layout: `internal/` защищает от импорта извне модуля.
3. Переезд выполнять отдельной задачей и только после закрытия блока A —
   не смешивать правки безопасности с перемещением файлов.

**Проверка:** ADR принят.

## T-043. Реализовать операции кошелька

**Статус:** ЗАВЕДЕНА

Из десяти требований [wallet/README.md](services/cmd/wallet/README.md) реализовано
чтение баланса и автосоздание. Нет списания, начисления, перевода,
транзакционности, истории, статусной модели.

**План**
1. Расширить [wallet.proto](middleware/wallet.proto): `Debit`, `Credit`,
   `Transfer`, `History`, `ChangeState`.
2. Операции — в одной транзакции БД с `SELECT ... FOR UPDATE` на кошельке:
   без этого конкурентные списания дают потерянное обновление.
3. Идемпотентность по ключу запроса — иначе повтор при таймауте спишет дважды.
4. Перенести изменение баланса из триггера в явный код: логика в триггере
   невидима из кода, не тестируется модульно и уже разошлась с бизнес-правилами.
5. Статусная модель с проверкой допустимых переходов
   (`DELETED` — терминальное состояние).
6. Пагинация истории.

**Проверка:** конкурентные тесты из T-034 на отсутствие потерянных обновлений.
