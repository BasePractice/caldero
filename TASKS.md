## T-051. Вход через соцсети и ЕСИА

**Статус:** ЗАВЕДЕНА

README: «регистрация пользователя в системе (в том числе через социальные сети,
ЕСИА, маркетплейсы?)». Не реализовано.

**План**
1. Решается вместе с T-041: если остаётся Keycloak — внешние провайдеры
   настраиваются в нём (identity brokering) и своего кода почти не требуют.
   Это сильный аргумент в пользу Keycloak, и его нужно учесть в ADR.
2. Модель связывания: один локальный пользователь — несколько внешних
   идентичностей; таблица `user_identities (provider, external_id, user_id)`.
3. Обработка коллизий: внешний аккаунт с почтой уже существующего пользователя
   не должен молча захватывать чужой профиль.
4. ЕСИА требует регистрации информационной системы и работы с УКЭП —
   зафиксировать в требованиях как внешнее ограничение, а не как код.
5. Маркетплейсы как провайдер входа: проверить, отдают ли OZON и WB OAuth
   для сторонних приложений; если нет — убрать пункт из требований
   (в README он и так помечен вопросом).

**Проверка:** вход через одного внешнего провайдера сквозным сценарием.

## T-078. Каналы оповещений: МАКС и электронная почта

**Статус:** ЗАВЕДЕНА

Канал подключается к уже существующему сервису оповещений (`services/cmd/notify`),
своей очереди и своих шаблонов не заводит.

К Telegram и сообщениям в приложении добавляются ещё два канала —
мессенджер МАКС и электронная почта. Почта нужна не только для оповещений:
подтверждение адреса идёт тем же каналом, и заводить для него
отдельную отправку нельзя.

**План**
1. Канал МАКС: выяснить, что даёт Bot API площадки — отправка сообщения
   по идентификатору чата, привязка аккаунта, признак блокировки бота.
   Начинать не с кода, а с ответа на этот вопрос: у Telegram и МАКС
   различаются и модель привязки, и коды ошибок.
2. Привязка аккаунта: тот же механизм кода с ограниченным сроком жизни,
   что и у Telegram, — общий, а не вторая реализация.
3. Канал почты: отправка через SMTP-релей провайдера. Учётные данные —
   в секретах; отправка с адреса, для которого настроены SPF, DKIM
   и DMARC, иначе письма уходят в спам и канал бесполезен.
4. Отписка от писем обязательна (`List-Unsubscribe` и ссылка в письме):
   рассылка без отписки — нарушение правил почтовых провайдеров
   и прямой путь в спам-листы.
5. Письмо собирается тем же шаблонизатором: тема и тело — отдельные
   шаблоны на тип события, HTML и текстовая часть.
6. Подтверждение адреса переводится на этот канал: сейчас код
   подтверждения уходит тем же событием, что и остальные оповещения.
7. Ограничения: у почты своё окно частоты, у МАКС — свои лимиты
   Bot API. Значения подбираются под реальные ограничения, а не наугад.
8. Схема: добавить значения каналов в `CHECK` таблиц `delivery`
   и `preference` отдельной миграцией.

**Проверка:** событие доходит до пользователя каждым из каналов;
блокировка бота и отказ SMTP не роняют бизнес-операцию и не приводят
к бесконечным повторам.

## T-079. Единый документ проекта в PDF через Typst

**Статус:** ЗАВЕДЕНА

Документация проекта разложена по десятку файлов: README, требования,
модель угроз, ADR, README сервисов, описание CI/CD. Прочитать проект
целиком нельзя — только собрать его в голове из кусков. Нужен один PDF,
который отдаётся человеку со стороны и отвечает на вопросы «что это»,
«из чего состоит», «как развернуть», «какие есть методы».

Typst выбран как источник: он собирает PDF одной командой, читается
и версионируется как текст, и не требует TeX-окружения.

**Что должно попасть в документ**

1. Назначение системы и функциональность: продуктовые сценарии из README
   и реестр требований со статусами.
2. Архитектура: контекст, контейнеры, границы, владение данными,
   диаграммы из `docs/architecture`.
3. Сервисы: назначение каждого, схема данных, зависимости, порты.
4. API: все методы по сервисам — путь, права, коды ответов, тела
   запроса и ответа. Это самая объёмная часть.
5. Развёртывание: переменные окружения, `docker compose`, миграции,
   CI и публикация образов.
6. Принятые решения: ADR списком с их сутью и условиями пересмотра.
7. Модель угроз и внешние ограничения.

**План**
1. Решить главное до вёрстки: **что является источником**. Документ,
   написанный руками отдельно от кода, устаревает через месяц. Разумный
   рубеж — текст пишется в Typst, а всё, что выводится из кода
   (список эндпоинтов, переменные окружения, таблица требований),
   генерируется скриптом в `.typ`-файлы и включается директивой `include`.
2. Источники генерации: маршруты — из `config/krakend/krakend.tmpl`
   и `registerHttpHandlers` каждого сервиса; переменные — из
   `services/config.go` и `.env.example`; требования — из
   `docs/requirements.md`; ADR — из `docs/adr/`.
3. Структура каталога `docs/book/`: `main.typ`, `chapters/*.typ`,
   `generated/*.typ`, общий стиль и титульный лист.
4. Цель `make docs` собирает PDF, `make docs-watch` — для правки.
   Сборка через контейнер с Typst, чтобы не требовать его установки.
5. Шаг в CI: документ собирается на каждый push, PDF публикуется
   артефактом сборки. Расхождение сгенерированных файлов с кодом —
   ошибка сборки, как `go mod tidy -diff`.
6. Русский текст: подобрать шрифт с кириллицей и зафиксировать его
   в репозитории или в образе, иначе PDF соберётся по-разному
   на разных машинах.

**Проверка:** `make docs` собирает PDF из чистого клона; изменение
эндпоинта без пересборки документа роняет CI.

## T-076. Адаптеры маркетплейсов OZON и WB

**Статус:** ЗАВЕДЕНА (нужен доступ к API)

Выделено из T-057. Контракт, кэширование, размыкатель цепи и заглушка
реализованы, решение записано в [ADR 0004](docs/adr/0004-marketplace-integration.md).
Осталось то, что нельзя сделать без доступа к API площадок.

**Что нужно выяснить до кода**

Публичные API OZON и WB ориентированы на продавца. Оформление заказа
от имени произвольного покупателя в них не предусмотрено. Пока не
подтверждено обратное, требование FR-24 «выбранный подарок заказывается
автоматически» может быть невыполнимым — и тогда переписывать нужно
требование, а не код.

**План**
1. Получить доступ к API хотя бы одной площадки и выяснить фактические
   возможности: карточка товара, цена, наличие, оформление заказа.
2. Рассмотреть партнёрские программы как основной источник карточек:
   они дают ссылки и данные о товаре, но заказ — вряд ли.
3. Реализовать адаптер, возвращающий `ErrUnsupported` для недоступных
   операций, а не имитирующий их.
4. Ключи API — в секретах, не в репозитории.
5. Учесть ограничения частоты: значения кэша подобрать под реальные лимиты,
   а не наугад.
6. Если оформление заказа недоступно — переписать FR-24 на сценарий
   со ссылкой и ручным заказом дарителем.

**Проверка:** карточка реального товара читается, а недоступные операции
честно возвращают `ErrUnsupported`.

## T-077. Подключение платёжного провайдера

**Статус:** ЗАВЕДЕНА (нужен договор и песочница)

Выделено из T-058. Контракт `payment.Gateway`, обработка вебхуков, сверка
и песочница реализованы, решение записано в [ADR 0005](docs/adr/0005-payment-flow.md).
Осталось то, что нельзя сделать без договора с платёжным агентом.

**Что нужно выяснить до кода**

Приём и вывод денежных средств требует статуса платёжного агента или
договора с ним (EXT-01). Песочницу провайдеры тоже выдают юридическому
лицу. Пока договора нет, FR-52 и FR-53 остаются реализованными только
против собственной песочницы, и это нужно называть своим именем,
а не выдавать за работающий платёжный контур.

**План**
1. Получить доступ к песочнице одного провайдера и выяснить фактические
   возможности: пополнение по СБП, выплата по номеру телефона, выплата
   на карту, привязка карты.
2. Адаптер провайдера поверх `payment.Gateway`: формат подписи вебхука,
   имена заголовков и разбор события подменяются полями `WebhookHandler`.
3. Хранилище операций в базе вместо `payment.Memory`: `Apply` — одна
   транзакция с блокировкой строки операции и журналом применённых
   событий. Разделять проверку повтора и запись нельзя.
4. Связать с кошельком: подтверждённое пополнение зачисляется через
   `Debit` с ключом идемпотентности, выплата — резервом и списанием,
   чтобы отказ провайдера не оставил деньги списанными.
5. Эндпоинт вебхука снаружи: маршрут на шлюзе, ограничение частоты,
   пустой `PAYMENT_WEBHOOK_SECRET` обязан отключать приём.
6. Регулярный запуск сверки (`PAYMENT_RECONCILE_INTERVAL`) и метрика
   числа незавершённых операций: без неё зависшие платежи не видны.
7. Ключи и секреты провайдера — в секретах, не в репозитории.
8. Комиссия: удержание при переводе денежного подарка по правилу
   из конфигурации.

**Проверка:** платёж проходит в песочнице провайдера; повторная доставка
вебхука не создаёт второго платежа; операция, о которой вебхук не дошёл,
завершается сверкой.

## T-066. Веб-интерфейс на Go WebAssembly

**Статус:** ЗАВЕДЕНА

У системы нет пользовательского интерфейса вообще. Единственная страница —
форма входа в собственном OAuth2-провайдере (T-061), и та отдаётся
серверным шаблоном. Проверить работу списка желаний, котла или кошелька
можно только через `curl` и коллекции в `_requests`.

Интерфейс на Go WebAssembly позволяет держать весь код на одном языке
и переиспользовать модели из `services/shared`, что для учебной цели №1
из README («писать на Go») даёт больше, чем отдельный фронтенд на JS.

**План**

1. **Проработка до кода.** Решение оформить как ADR: WASM даёт единый язык
   и общие модели, но платит за это размером бандла (даже с `tinygo` это
   сотни килобайт против десятков у JS), отсутствием SSR и слабой
   экосистемой UI-компонентов. Зафиксировать, что именно перевешивает.
2. **Выбор подхода:** `syscall/js` вручную, либо фреймворк
   (`vugu`, `go-app`, `vecty`). Критерии: живость проекта, размер бандла,
   отладка. Не перечислять варианты в отчёте — выбрать один и обосновать.
3. **Сборка:** `GOOS=js GOARCH=wasm`, `wasm_exec.js` из дистрибутива Go,
   отдельная цель в `Makefile` (T-029) и шаг в CI (T-030).
   Проверить, оправдывает ли `tinygo` усложнение сборки.
4. **Раздача статики:** отдельный сервис или nginx в compose; маршрут
   на шлюзе. Не подмешивать статику к API-сервисам.
5. **Аутентификация из браузера:** Authorization Code Flow с PKCE
   (T-061 уже реализован). Токен не хранить в `localStorage` — он доступен
   любому скрипту на странице; либо httpOnly-cookie, либо только в памяти
   с молчаливым обновлением.
6. **CORS и WebSocket:** сейчас `allow_origins` сужен до localhost (T-001),
   origin интерфейса нужно будет добавить явно — и туда же,
   в `NOTIFY_WS_ORIGINS`, иначе браузер не откроет сокет оповещений.
   KrakenD Community Edition WebSocket не проксирует (EXT-05): маршрут
   до `notify:51055/notify/ws` придётся вести мимо шлюза — через тот же
   nginx, что раздаёт статику. Пока его нет, интерфейс работает
   на длинном опросе.
7. **Экраны первой очереди:** вход, профиль (T-050), кошелёк (T-043),
   список желаний. Остальное — по мере появления сервисов.
8. **Переиспользование моделей:** типы из `services/shared` компилируются
   и под `js/wasm`, но `database/sql` и драйверы — нет. Проверить, что
   общие пакеты не тянут серверные зависимости, иначе их придётся разделять.

**Зависит от:** ничего не блокирует — профиль, кошелёк и список желаний
уже реализованы, и первым экранам есть что показывать. Разумно начать
с ADR и каркаса сборки, а экраны добавлять вслед за сервисами.

**Проверка:** страница открывается через шлюз, проходит вход по PKCE
и показывает данные профиля, полученные из API.

4. Стратегия выката и откат: что откатывается — образ, схема, оба.

6. Защита ветки `main` и обязательное прохождение CI перед слиянием.

**Проверка:** выкат и откат опробованы на staging.

## T-073. Срок хранения истории транзакций и архивация партиций

**Статус:** ЗАВЕДЕНА

Выделено из T-067. Партиции транзакций теперь создаются автоматически
вперёд, но назад не убираются: таблица растёт бесконечно, просто
по месячным кускам.

Решать это без ответа на вопрос «сколько лет хранится история операций»
нельзя, а такого требования в проекте нет — нефункциональные требования
вообще не зафиксированы (T-045).

**План**
1. Зафиксировать срок хранения в реестре требований (T-045). Для денежных
   операций он обычно определяется не удобством, а регуляторными
   требованиями — это нужно проверить, а не придумать.
2. Отсоединение старых партиций (`DETACH PARTITION`) вместо удаления:
   отсоединённая таблица остаётся доступной для выгрузки.
3. Выгрузка в холодное хранилище и только затем удаление.
4. Метрика: возраст самой старой партиции.
5. Учесть в модели угроз (T-046): удаление финансовой истории — операция,
   которую нельзя отменить, и права на неё должны быть отдельными.

**Проверка:** партиция старше срока хранения отсоединяется, данные
остаются доступны для выгрузки.

## T-080. Ужесточить схему: телефон обязателен на уровне базы

**Статус:** ЗАВЕДЕНА

Выделено из подтверждения контактов. Телефон обязателен по требованию,
и регистрация без него отклоняется в коде, но колонка `users.phone`
остаётся nullable: у записей, созданных до появления профиля, телефона нет,
и объявить `NOT NULL` одним шагом нельзя.

**План**
1. Выяснить, сколько записей без телефона осталось: если ни одной,
   ужесточение — это одна строка миграции.
2. Если записи есть — решить, что с ними: заполнять телефон за пользователя
   нельзя, значит нужен либо срок на дозаполнение с последующим удалением
   учётной записи, либо отдельное состояние «профиль неполон».
3. Миграция `ALTER COLUMN phone SET NOT NULL` после дозаполнения.
4. Проверить, что подтверждение телефона при этом остаётся отдельным
   признаком: `NOT NULL` гарантирует заполненность, а не то, что номер
   принадлежит пользователю.

**Проверка:** запись без телефона в схему не проходит; существующие
пользователи не потеряли доступ.
