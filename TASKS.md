## T-011. `credit.Get` не выбирает поля, от которых зависит расчёт

**Статус:** ЗАВЕДЕНА

[credit/db.go:30-32](services/cmd/credit/db.go:30) не читает `already_payed`,
`created_at`, `last_payed_at` — а именно они управляют расчётом. Для частично
погашенного кредита график всегда считается как для нового.

**План**
1. Добавить недостающие колонки в `SELECT` и в `Scan`.
2. `last_payed_at` nullable — сканировать в `sql.NullTime` и преобразовывать.
3. `Get` должен возвращать `sql.ErrNoRows` наружу обёрнутым, чтобы обработчик
   отличал 404 от 500 (сейчас любая ошибка → `Not found`).

**Проверка:** тест на репозитории из T-034.

## T-012. Неверный `GROUP BY` в запросе кошелька

**Статус:** ЗАВЕДЕНА

[wallet/db.go:33-44](services/cmd/wallet/db.go:33) — `GROUP BY t.value, wlt.id`
разбивает агрегат по номиналу: вместо суммы получается строка на каждую сумму,
а `LEFT JOIN` размножает строки кошелька.

**План**
1. `GROUP BY wlt.id` в обоих CTE (`trans_debit`, `trans_credit`).
2. `LEFT JOIN wlt` → `JOIN wlt`: сейчас сканируется вся таблица `transaction`
   вместе с чужими транзакциями.
3. Отфильтровать удалённые кошельки (`state <> 'DELETED'`).
4. Вынести SQL в константу, синхронизировать с
   [wallet/README.md](services/cmd/wallet/README.md), где лежит та же ошибка.

**Проверка:** тест из T-034 с двумя транзакциями одинакового номинала.

## T-013. Гонка при автосоздании кошелька

**Статус:** ЗАВЕДЕНА

[wallet/db.go:27-89](services/cmd/wallet/db.go:27) — «нет строк → INSERT → `goto next`».
Параллельные запросы одного пользователя дают нарушение `UNIQUE (user_id, type)`.
Плюс `defer rows.Close()` внутри цикла с `goto` накапливает отложенные вызовы.

**План**
1. Заменить на `INSERT INTO wallet (user_id) VALUES ($1) ON CONFLICT (user_id, type) DO NOTHING`
   перед выборкой — один проход без `goto` и без цикла.
2. Проверить `rows.Err()` после цикла (сейчас не проверяется — потеря ошибок).
3. `rows.Close()` через явный `defer` в правильной области видимости.

**Проверка:** `go test -race` на конкурентном тесте из T-034.

## T-016. Единый bootstrap сервиса + graceful shutdown

**Статус:** ЗАВЕДЕНА

Четыре `main.go` совпадают почти дословно, и в каждом продублированы одни и те же
дефекты. [services/exit.go:11-19](services/exit.go:11) возвращает
`context.Background()` — контекст, который никогда не отменяется, поэтому отмена
по сигналу до обработчиков не доходит, а `os.Exit(0)` рвёт активные запросы.

**План**
1. `services.Run(name string, run func(ctx context.Context) error) ` — общая точка входа:
   конфигурация, логирование, метрики, сигнальный контекст, код возврата.
2. `signal.NotifyContext` с возвратом производного контекста; `defer cancel()`.
3. HTTP: `srv.Shutdown(ctx)` с таймаутом; gRPC: `GracefulStop()` с таймаутом
   и `Stop()` по его истечении.
4. Закрытие пула БД и Redis после остановки сервера.
5. Удалить `exit.go` и `recover()` в `main` — он не ловит паники обработчиков
   и создаёт ложное ощущение защищённости. Вместо него — recover-middleware
   на mux и `grpc_recovery` интерсептор.

**Проверка:** SIGTERM во время долгого запроса — запрос завершается, процесс выходит с 0.

## T-018. Таймауты `http.Server`, ограничение размера тела запроса

**Статус:** ЗАВЕДЕНА

Все три HTTP-сервиса используют `http.ListenAndServe` без таймаутов (Slowloris),
`json.NewDecoder(r.Body)` читает неограниченный объём.

**План**
1. Явный `&http.Server{ReadHeaderTimeout, ReadTimeout, WriteTimeout, IdleTimeout}`.
2. `http.MaxBytesReader` на теле запроса.
3. `decoder.DisallowUnknownFields()` — опечатка в поле должна быть ошибкой,
   а не молчаливым нулевым значением.
4. Ограничение размера и на gRPC: `grpc.MaxRecvMsgSize`.

**Проверка:** запрос с телом больше лимита → `413`.

## T-019. `/me`: claims из introspection вместо парсинга JWT

**Статус:** ЗАВЕДЕНА

[service.go:170-194](services/cmd/users/service.go:170) — `CoreStrategy` это
HMAC-стратегия, access-токен непрозрачен и не является JWT, но подаётся
в `jwt.ParseWithClaims`. Разбор не может завершиться успешно никогда.
Результат `IntrospectToken` при этом отбрасывается через `_, _, err :=`.

**План**
1. Взять `AccessRequester` из `IntrospectToken` и достать сессию из него.
2. Отдавать наружу только нужные поля (`sub`, `exp`, `scope`), а не весь
   `MapClaims`: сейчас в ответ уходит всё содержимое сессии.
3. Не возвращать `err.Error()` клиенту — только `401` без деталей.

**Проверка:** валидный токен → `200` с subject; протухший → `401`.

## T-022. Закрыть statsviz за флагом конфигурации

**Статус:** ЗАВЕДЕНА

`statsviz` публикует внутреннее состояние рантайма (heap, горутины, GC)
без какой-либо аутентификации на порту метрик во всех четырёх сервисах.
Для отладки это удобно, для продакшена — утечка внутреннего состояния.

Разбор `LOG_COLOR` через `ParseBool`, удаление флага `-mport`, регистрируемого
после `flag.Parse()`, и логирование ошибки `ListenAndServe` уже сделаны
вместе с введением `services.Config`.

**План**
1. Включать `statsviz` только при `DEBUG_STATSVIZ=true`, по умолчанию выключен.
2. Порт метрик держать отдельно от публичного порта сервиса и не публиковать
   его наружу (сейчас он и так за пределами шлюза, но это нигде не закреплено).
3. Когда появится `/metrics` во всех сервисах (T-036), развести служебный
   и публичный обработчики по разным `ServeMux`.

**Проверка:** без переменной окружения `/debug/statsviz` недоступен.

## T-060. Хранение сессии токена: `fosite.Request` не десериализуется

**Статус:** ЗАВЕДЕНА

Найдено при работе над T-003 и подтверждено прогоном.
[users/db.go:244-247](services/cmd/users/db.go:244) делает
`json.Unmarshal(data, &req)` в `fosite.Request`, у которого поля `Client`
и `Session` — интерфейсы. Десериализация падает:

```
json: cannot unmarshal object into Go struct field Request.client of type fosite.Client
```

`getTokenSession` не может вернуть сессию **никогда**, поэтому не работают
introspection, refresh и проверка access-токена. Переданный в метод параметр
`session fosite.Session` при этом полностью игнорируется — а он и есть тот
экземпляр, в который fosite ожидает разложить данные.

**План**
1. Ввести собственный DTO хранения вместо сериализации `fosite.Request`
   целиком: идентификатор запроса, client_id, scopes, granted scopes,
   audience, requested_at и отдельно сериализованная сессия.
2. При чтении собирать `fosite.Request` вручную: клиента поднимать через
   `GetClient`, сессию раскладывать в переданный `session` — он приходит
   конкретным типом (`*openid.DefaultSession`) и корректно принимает JSON.
3. Заполнять `GrantedScope` и `GrantedAudience` — без них проверка scope
   на защищённых эндпоинтах не сработает.
4. Тест на полный цикл: сохранить сессию, прочитать, сверить поля.
   Такой тест и должен был поймать дефект.

**Проверка:** сохранённый токен успешно проходит introspection;
refresh выдаёт новую пару.

Схема заложена под сценарий «оператор выдаёт кредит клиенту»
(`user_id` + `creator_id`), но самой роли оператора в системе нет:
все пользователи равны в правах.

Для `account` та же дыра закрыта временным решением — счёт заводится только
себе. Это ограничение, а не ролевая модель.

**План**
1. Определить роли: пользователь, оператор, администратор. Источник ролей —
   claim токена, а не таблица в каждом сервисе.
2. Проверка роли на уровне middleware, а не в каждом обработчике.
3. Для `credit`: выдача кредита другому пользователю — только роль оператора.
4. Для `account`: снять временное ограничение «только себе» и заменить
   проверкой роли.
5. Согласовать с T-041: если остаётся Keycloak, роли берутся из
   `realm_access.roles` — шлюз уже умеет их пробрасывать.
6. Записать решение в модель угроз (T-046): повышение привилегий.

**Проверка:** обычный пользователь не может выдать кредит другому.
