3. Убрать `--web.enable-admin-api` у Prometheus.
4. Приватные RSA-ключи в БД по-прежнему без шифрования. Собственный провайдер
   решено оставить (см. `docs/adr/0001-auth-provider.md`), поэтому шифрование

Секрет тестового клиента уже переведён на bcrypt-хеш миграцией 3: `fosite`
сравнивает `GetHashedSecret()` через bcrypt, и открытый текст не совпадал
никогда — аутентификация клиента возвращала `invalid_client`.

**Проверка:** `git grep` по известным паролям пуст.

## T-040. Починить или удалить цепочку логов filebeat → logstash

**Статус:** ЗАВЕДЕНА

`filebeat` закомментирован в [docker-compose.yml:68-75](docker-compose.yml:68),
`LOG_FILE` закомментирован у всех сервисов — цепочка разорвана в двух местах,
логи в Kibana не попадают. В [logstash.conf](config/logstash/logstash.conf)
`document_id => "%{[parsed][uuid]}"`, но `slog` поля `uuid` не пишет: все записи
получат один литеральный id и будут перезаписывать друг друга.

**План**
1. Решить: файловые логи + filebeat или сразу GELF в logstash.
2. Добавить в `slog` поля `uuid`/`trace_id` (связать с T-037).
3. Либо включить цепочку целиком, либо удалить filebeat и его конфиг,
   чтобы не создавать видимость работающей интеграции.

**Проверка:** запись из сервиса видна в Kibana с уникальным `_id`.

## T-042. ADR: миграция на `pgx` и layout `internal/`

**Статус:** ЗАВЕДЕНА

`RULE.md` предписывает `pgx` и `internal/<домен>/`, кодовая база использует
`database/sql` + `lib/pq` и `services/cmd/...`. Сам `RULE.md` отдаёт приоритет
существующим соглашениям, поэтому расхождение оформляется решением, а не
молчаливой переделкой.

**План**
1. ADR: остаёмся на `database/sql` или переезжаем на `pgx`.
   Аргумент за переезд — `lib/pq` в режиме поддержки, `pgx` даёт
   `COPY`, слушателей и нормальные типы.
2. Решение по layout: `internal/` защищает от импорта извне модуля.
3. Переезд выполнять отдельной задачей и только после закрытия блока A —
   не смешивать правки безопасности с перемещением файлов.

**Проверка:** ADR принят.

## T-049. gRPC как основной транспорт между сервисами (цель 6)

## T-066. Веб-интерфейс на Go WebAssembly

**Статус:** ЗАВЕДЕНА

У системы нет пользовательского интерфейса вообще. Единственная страница —
форма входа в собственном OAuth2-провайдере (T-061), и та отдаётся
серверным шаблоном. Проверить работу списка желаний, котла или кошелька
можно только через `curl` и коллекции в `_requests`.

Интерфейс на Go WebAssembly позволяет держать весь код на одном языке
и переиспользовать модели из `services/shared`, что для учебной цели №1
из README («писать на Go») даёт больше, чем отдельный фронтенд на JS.

**План**

1. **Проработка до кода.** Решение оформить как ADR: WASM даёт единый язык
   и общие модели, но платит за это размером бандла (даже с `tinygo` это
   сотни килобайт против десятков у JS), отсутствием SSR и слабой
   экосистемой UI-компонентов. Зафиксировать, что именно перевешивает.
2. **Выбор подхода:** `syscall/js` вручную, либо фреймворк
   (`vugu`, `go-app`, `vecty`). Критерии: живость проекта, размер бандла,
   отладка. Не перечислять варианты в отчёте — выбрать один и обосновать.
3. **Сборка:** `GOOS=js GOARCH=wasm`, `wasm_exec.js` из дистрибутива Go,
   отдельная цель в `Makefile` (T-029) и шаг в CI (T-030).
   Проверить, оправдывает ли `tinygo` усложнение сборки.
4. **Раздача статики:** отдельный сервис или nginx в compose; маршрут
   на шлюзе. Не подмешивать статику к API-сервисам.
5. **Аутентификация из браузера:** Authorization Code Flow с PKCE
   (T-061 уже реализован). Токен не хранить в `localStorage` — он доступен
   любому скрипту на странице; либо httpOnly-cookie, либо только в памяти
   с молчаливым обновлением.
6. **CORS:** сейчас `allow_origins` сужен до localhost (T-001), origin
   интерфейса нужно будет добавить явно.
7. **Экраны первой очереди:** вход, профиль (T-050), кошелёк (T-043),
   список желаний (T-052). Остальное — по мере появления сервисов.
8. **Переиспользование моделей:** типы из `services/shared` компилируются
   и под `js/wasm`, но `database/sql` и драйверы — нет. Проверить, что
   общие пакеты не тянут серверные зависимости, иначе их придётся разделять.

**Зависит от:** T-050, T-043, T-052 — до появления самих сервисов
показывать в интерфейсе почти нечего. Разумно начать с ADR и каркаса
сборки, а экраны добавлять вслед за сервисами.

**Проверка:** страница открывается через шлюз, проходит вход по PKCE
и показывает данные профиля, полученные из API.

## T-067. Автоматическое создание партиций транзакций

**Статус:** ЗАВЕДЕНА

Выделено из T-025. Партиции создаются миграцией на окно от года назад
до двух лет вперёд. Когда окно закончится, все новые транзакции пойдут
в партицию `transaction_default` — она не упадёт, но и смысла
в партиционировании не останется: одна таблица снова будет расти без границ.

**План**
1. Функция в БД, создающая партицию следующего месяца, если её ещё нет.
2. Запуск: воркер в сервисе кошелька с интервалом из конфигурации либо
   `pg_cron`. `pg_cron` тянет расширение в образ PostgreSQL, поэтому
   воркер выглядит дешевле — но решение стоит записать явно.
3. Горутина воркера обязана завершаться по контексту (`RULE.md`).
4. Мониторинг: метрика «сколько строк лежит в `transaction_default`».
   Ненулевое значение означает, что окно кончилось и это осталось незамеченным.
5. Отдельно решить судьбу старых партиций: отсоединение и архивация
   либо удаление по сроку хранения. Срок хранения истории транзакций
   в требованиях не зафиксирован (T-045).

**Проверка:** партиция следующего месяца появляется без ручного вмешательства,
`transaction_default` остаётся пустой.

## T-068. Отказаться от гранта password

**Статус:** ЗАВЕДЕНА

Найдено линтером при работе над T-030: `compose.OAuth2ResourceOwnerPasswordCredentialsFactory`
помечен в fosite как устаревший (SA1019) и исключён из OAuth 2.1.

Причина в самом устройстве гранта: клиент получает пароль пользователя
в открытом виде. Это исключает внешних провайдеров входа (T-051),
не даёт применить второй фактор и требует доверять каждому клиенту так же,
как самому серверу авторизации.

Грант оставлен, потому что на нём держатся коллекции в `_requests` и часть
проверок. Authorization Code Flow с PKCE (T-061) уже реализован и покрывает
те же сценарии без этих недостатков.

**План**
1. Перевести коллекции `_requests` на authorization code + PKCE (T-035).
2. Убрать `password` из `grant_types` отладочного клиента миграцией.
3. Снять фабрику и `//nolint:staticcheck` в `newService`.
4. Убрать выдачу scope для password-гранта в `handleToken` — она станет
   ненужной вместе с самим грантом.
5. Проверить, что ничего, кроме коллекций, на грант не опиралось.

**Проверка:** запрос с `grant_type=password` отклоняется как
`unsupported_grant_type`, сквозной сценарий на authorization code проходит.
