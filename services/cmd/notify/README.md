# Оповещения

Сервис доставляет пользователю события системы: резерв подарка, приглашение
в котёл, смену его состояния, итог розыгрыша, завершение платежа, код
подтверждения.

## Функциональные требования

1. Telegram-бот (реализовано: привязка по коду, отправка, обработка блокировки);
2. WebSocket для активных сессий (реализовано: `GET /notify/ws`);
3. Пулинг «как в вк» (реализовано: `GET /notify/messages?after=&wait=` —
   запрос ждёт появления сообщения и возвращает его без нового опроса);
4. Настройки пользователя: какие события и в какой канал (реализовано:
   `GET`/`PUT /notify/preferences`).

5. Мессенджер МАКС (механизм готов: протокол задаётся конфигурацией,
   значения — по документации площадки);
6. Электронная почта (реализовано: письмо с текстовой и HTML-частью,
   отписка в один клик).

## Как устроено

**Публикация не ждёт доставки.** `POST /notify/events` кладёт событие
в очередь и отвечает `202`. Отправка в Telegram не должна ни задерживать
бизнес-операцию, ни откатывать её при сбое: подарок остаётся подаренным,
даже если бот недоступен.

**Очередь — таблица `delivery`.** Воркер арендует задания запросом
с `FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров сервиса
разбирают очередь параллельно, не мешая друг другу. Неудачная попытка
откладывается с растущей задержкой, после шести попыток задание снимается
с доставки.

**WebSocket и длинный опрос — один канал.** Оба отдают одно и то же:
ленту `message`. Считай их разными каналами, пользователь с открытой
вкладкой и работающим опросом получал бы каждое событие дважды. Источник
правды — лента; хаб и шина Redis нужны только для мгновенной доставки,
а пропущенное клиент забирает по курсору.

**Повторы отсекаются дважды.** Публикующий сервис передаёт `dedup_key`,
и второе событие с тем же ключом не создаётся. Внутри одно событие даёт
не более одной доставки в канал и не более одного сообщения в ленте:
повтор после сбоя не покажет дубль.

**Тексты — в шаблонах** (`templates/messages.tmpl`), отдельно от кода.
Отсутствие обязательной подстановки — ошибка, а не пустая строка:
сообщение с дырой посреди фразы хуже недоставленного.

## Каналы

**Бот — это протокол, а не отдельный код.** У Telegram и МАКС один
и тот же набор действий: отправить сообщение, забрать обновления, узнать
о блокировке. Различаются адреса и имена полей, поэтому они вынесены
в конфигурацию: для Telegram значения заданы по умолчанию, потому что его
формат известен, а для остальных площадок приходят извне. Выдумывать чужой
протокол нельзя — канал с неполной настройкой роняет старт, а не молчит.

Привязка аккаунта общая: код с ограниченным сроком, хеш в базе, ответ бота
не различает «нет кода» и «просрочен».

**Почта берёт адрес из профиля**, а не хранит свою копию: вторая копия
разойдётся с профилем при первой же смене адреса. За контактами сервис
ходит в `users` с ролью оператора — контакты это персональные данные,
и по идентификатору кому угодно они не отдаются.

Письмо уходит только на подтверждённый адрес. Исключение одно — код
подтверждения самого адреса: иначе доставить его некуда.

**Отписка обязательна.** В письме есть `List-Unsubscribe`,
`List-Unsubscribe-Post` и ссылка в тексте; рассылка без отписки нарушает
правила почтовых провайдеров и ведёт в спам-листы. Ссылка подписана: без
подписи достаточно подставить чужой идентификатор, чтобы отписать
постороннего. Отписка выключает канал целиком — человек просит не писать
ему больше, а не настроить фильтры.

Письмо собирается из тех же шаблонов, что и остальные сообщения, и имеет
текстовую и HTML-часть: клиент без HTML иначе покажет пустое письмо,
а письмо без текстовой части хуже проходит фильтры.

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/notify/events` | Публикация события. Чужому пользователю — только с ролью оператора |
| `GET` | `/notify/messages?after=&limit=&wait=` | Лента по курсору, с длинным опросом до 20 секунд |
| `GET` | `/notify/ws` | WebSocket активной сессии |
| `GET` | `/notify/preferences` | Настройки доставки |
| `PUT` | `/notify/preferences` | Изменение настроек |
| `POST` | `/notify/messengers/{provider}/link` | Код привязки бота |
| `GET` | `/notify/messengers/{provider}` | Состояние привязки |
| `GET` | `/notify/unsubscribe` | Отписка от писем по ссылке из письма |

Примеры запросов — в [_requests/notify.http](../../../_requests/notify.http).

## Настройка

Канал Telegram включается токеном бота (`NOTIFY_TELEGRAM_TOKEN`), МАКС —
токеном и описанием протокола (`NOTIFY_MAX_*`), почта — настройками SMTP
вместе с адресом отправителя и ссылкой отписки. Без них сервис работает:
лента приложения не зависит ни от ботов, ни от релея.

Ограничение частоты (`NOTIFY_RATE_LIMIT`, `NOTIFY_RATE_WINDOW`) действует
на пару «пользователь + канал»: без него цепочка смен состояния котла
превращается в поток сообщений. Превышение откладывает сообщение,
а не отменяет его.

## Ограничения

- KrakenD Community Edition не проксирует WebSocket (EXT-05): снаружи
  доступен длинный опрос, а `GET /notify/ws` — только внутри контура,
  пока не появится отдельный маршрут (T-066).
- Решения и их причины — в [ADR 0006](../../../docs/adr/0006-notification-delivery.md).
