# Кошелек

Внутренний учёт средств: балансы, операции и их история. Кошелёк — единственное
место, где меняются деньги пользователя, и единственный сервис, говорящий
по gRPC.

## Функциональные требования

1. Хранить баланс внутренней валюты системы (реализовано);
2. Выполнять операции по списанию и начислению валюты (реализовано: `Debit`, `Credit`);
3. Выполнять операции перевода валюты с одного кошелька на другой (реализовано: `Transfer`);
4. Обеспечивать транзакционность операций. Работать в синхронном и асинхронном режиме
   (реализовано: блокировка строки кошелька, ключ идемпотентности, а также
   резервирование средств — `Reserve`, `Confirm`, `Reject`);
5. Хранение истории операций (транзакций) (реализовано: `History` с постраничной выдачей);
6. Партиционирование таблиц транзакций по критериям: время создание транзакции и разделением за один месяц (реализовано: `PARTITION BY RANGE (created_at)`, окно партиций продлевается вперёд обслуживающим воркером, партиции старше срока хранения отсоединяются назад);
7. Поддерживать разные типы кошельков, а именно: пользовательский и общий;
8. Разные типы кошельков, пока только один (PLAIN). У пользователя может быть только один кошелек одного типа;
9. Статусная модель кошелька: ACTIVE, BLOCKED, DELETED, CLOSED. Из состояния CLOSE, BLOCKED можно перейти в состояние
   ACTIVE, но состояние DELETE является терминальным (реализовано: `ChangeState`,
   терминальность DELETED обеспечивается триггером);
10. Если у сервиса запрашивается кошелек для пользователя и его не существует, он создается автоматически с типом PLAIN
    и статусом ACTIVE (реализовано; тип в схеме называется `USER`, а не `PLAIN`);

## Идемпотентность

Все операции, меняющие баланс, требуют `idempotency_key`. Это не удобство:
клиент не может отличить «запрос не дошёл» от «ответ не дошёл», и без ключа
повтор при обрыве связи проведёт операцию второй раз. Повторный вызов
с тем же ключом возвращает результат первой операции.

## Резервирование

Асинхронный сценарий: `Reserve` откладывает средства, `Confirm` списывает их,
`Reject` освобождает. Баланс при резервировании не меняется — уменьшается
доступный остаток. Это существенно: пока операция не подтверждена, средства
ещё принадлежат владельцу, но потратить их второй раз он не может.

Все проверки достаточности средств идут от доступного остатка, а не от
баланса. Иначе одни и те же средства можно было бы зарезервировать дважды
или списать в обход резерва.

У резерва есть срок жизни: брошенный резерв без него блокировал бы средства
навсегда. Просроченные освобождаются воркером.

## Срок хранения истории

Партиции месячные, и обслуживающий воркер работает с обоими краями окна:
вперёд создаёт недостающие, назад отсоединяет всё старше срока хранения
(`TRANSACTION_RETENTION_MONTHS`, по умолчанию 72 месяца — см. NFR-05).

**Отсоединяет, а не удаляет.** `DETACH PARTITION` оставляет таблицу
в схеме: запросы истории её больше не видят, но данные никуда не деваются
и выгружаются обычным `pg_dump`. Удаление финансовой истории необратимо,
и делать его по расписанию нельзя — это работа человека с отдельными
правами.

Баланс отсоединение не задевает: он хранится в самом кошельке и меняется
триггером при проведении транзакции, а не пересчитывается по истории.
Иначе архивация превращалась бы в списание денег.

Возраст самой старой присоединённой партиции публикуется метрикой
`wish_transaction_oldest_partition_age_days`: без неё обслуживание либо
идёт, либо молча не идёт, и узнать об этом можно только по размеру таблицы.

## Конкурентный доступ

Кошелёк блокируется на время операции (`SELECT ... FOR UPDATE`). Без этого
два одновременных списания прочитали бы один и тот же баланс, и одно из них
потерялось бы. При переводе кошельки блокируются в порядке идентификаторов —
иначе встречные переводы дают взаимную блокировку.

### Запросы

Получаем информацию о кошельках пользователя

```sql
WITH wlt AS (SELECT *
             FROM wallet
             WHERE user_id = '4d91fbf0-07a7-4a0d-8b41-19e90f4540c0'
               AND state <> 'DELETED'),
     trans_debit AS (SELECT SUM(t.value) AS value, wlt.id
                     FROM transaction t
                              JOIN wlt ON t.target = wlt.id
                     WHERE t.state = 'RESERVED'
                       AND t.operation = 'DEBIT'
                     GROUP BY wlt.id),
     trans_credit AS (SELECT SUM(t.value) AS value, wlt.id
                      FROM transaction t
                               JOIN wlt ON t.target = wlt.id
                      WHERE t.state = 'RESERVED'
                        AND t.operation = 'CREDIT'
                      GROUP BY wlt.id),
     trans AS (SELECT COUNT(t.id) AS count, wlt.id
               FROM transaction t
                        JOIN wlt ON t.target = wlt.id
               GROUP BY wlt.id)
SELECT wlt.id                          AS id,
       wlt.state                       AS state,
       wlt.type                        AS type,
       wlt.balance                     AS balance,
       COALESCE(trans.count, 0)        AS trans_c,
       COALESCE(trans_debit.value, 0)  AS dbt_value,
       COALESCE(trans_credit.value, 0) AS crd_value
FROM wlt
         LEFT JOIN trans ON wlt.id = trans.id
         LEFT JOIN trans_debit ON wlt.id = trans_debit.id
         LEFT JOIN trans_credit ON wlt.id = trans_credit.id
ORDER BY wlt.created_at;
```
