# Пользователи и доступ

Сервис отвечает за учётные записи, профиль, роли и весь контур OAuth2:
выдачу токенов, ключи подписи и их ротацию.

## Функциональные требования

1. Регистрация пользователя (реализовано: `POST /register`);
2. Профиль: аватар, почта, телефон, пол (реализовано: `GET`/`PATCH /profile`,
   публичная карточка `GET /users/{id}` без контактов);
3. Уникальный идентификатор и просмотр карточки по нему (реализовано);
4. JWT и инфраструктура OAuth2 (реализовано: authorization code с PKCE,
   RS256, JWKS, ротация ключей);
5. Роли и разграничение прав (реализовано: роли приходят claim'ом токена);
6. Подтверждение телефона и почты (реализовано, см. ниже).

7. Вход через социальные сети (реализовано, см. ниже). ЕСИА не реализуема
   в учебном контуре: она требует регистрации информационной системы
   и работы с УКЭП (EXT-02).

## Подтверждение контактов

Обязательность поля — это ещё не подтверждение: пользователь может ввести
чужой или несуществующий номер. Поэтому телефон и почта подтверждаются
кодом, а признаки `phone_confirmed` и `email_confirmed` живут отдельно
от самих значений.

- **Код не возвращается в ответе API** — он уходит на контакт через сервис
  оповещений. Иначе подтверждение ничего не подтверждает.
- **В базе лежит хеш кода**, а не код: таблица с кодами — это список
  готовых способов подтвердить чужой контакт. Ключ хеширования — общий
  секрет сервиса, поэтому по одной украденной базе шестизначный код
  не перебрать. В хеш входят пользователь, вид и сам контакт: код,
  выданный одному, не подойдёт другому.
- **Срок жизни и число попыток ограничены.** Шесть цифр — это выбор
  в пользу человека, который вводит код руками; стойкость обеспечивают
  пятнадцать минут жизни и пять попыток, после которых код сгорает.
- **Частота отправки ограничена дважды**: паузой между сообщениями
  и пределом за окно. Без этого эндпоинт отправки превращается в средство
  слать сообщения на чужой номер за наш счёт. Тот же предел стоит
  и на шлюзе — по IP.
- **Почте уходит ссылка**, а не код: токен в тридцать два байта руками
  никто не переписывает.
- **Смена контакта сбрасывает подтверждение**, а код от прежнего номера
  новый не подтверждает — контакт сверяется в той же транзакции, что
  и отметка.
- **Код подтверждения по умолчанию не уходит в Telegram**: до подтверждения
  привязки бот может быть чужим, а код — это доступ к учётной записи.

Неподтверждённый контакт нельзя использовать для восстановления доступа
и для доставки кодов в мессенджер (EXT-06). Учётная запись при этом
не блокируется: блокировка наказывала бы пользователя за нашу
неспособность доставить код.

## Вход через внешних провайдеров

**Провайдер задаётся конфигурацией, а не кодом.** VK, Яндекс, Google
и прочие различаются адресами и названиями полей профиля, но не потоком:
это один и тот же authorization code flow. Писать под каждого свой адаптер
значило бы копировать один и тот же обмен кода на токен. Пути к полям
профиля тоже конфигурация: у одних это `email`, у других `response.email`.

**Совпадение почты не отдаёт чужой профиль.** Это главная ловушка внешнего
входа: почта у провайдера может быть не подтверждена, и автоматическое
связывание по ней позволяет захватить чужую учётную запись, просто заведя
ящик с нужным адресом. Поэтому первый вход через провайдера создаёт нового
пользователя, а почта провайдера остаётся справочной в самой идентичности
и в профиль не переносится. Связать внешний аккаунт с существующим можно
только изнутри — уже войдя в него.

**Состояние входа одноразовое и живёт в базе.** `state` защищает
от подделки ответа, PKCE — от использования перехваченного кода, а хранение
в базе нужно потому, что ответ провайдера может прийти на другой экземпляр
сервиса. Состояние удаляется при чтении, поэтому повторно предъявленный
ответ не сработает; брошенные состояния убирает фоновая задача.

**Последний способ входа отвязать нельзя.** У пользователя, созданного
через провайдера, пароля нет — отвязка единственной идентичности отобрала
бы у него доступ. Признак `password_set` и отличает «пароль не задан»
от «задан».

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/register` | Регистрация |
| `POST` | `/token`, `GET`/`POST` `/auth` | Контур OAuth2 |
| `GET` | `/me` | Данные владельца токена |
| `GET`/`PATCH` | `/profile` | Свой профиль |
| `POST` | `/profile/confirmations` | Запросить код подтверждения |
| `POST` | `/profile/confirmations/verify` | Предъявить код |
| `GET` | `/auth/social/{provider}` | Начать вход через провайдера |
| `GET` | `/auth/social/{provider}/callback` | Возврат от провайдера |
| `GET` | `/profile/identities` | Способы внешнего входа |
| `POST` | `/profile/identities/{provider}` | Привязать внешний аккаунт |
| `DELETE` | `/profile/identities/{provider}` | Отвязать внешний аккаунт |
| `GET` | `/users/{id}` | Публичная карточка без контактов |
| `GET` | `/.well-known/jwks.json` | Ключи проверки подписи |
| `POST` | `/clients`, `/rotate-keys`, `/revoke` | Служебные, под административным токеном |

Примеры запросов — в [_requests/users.http](../../../_requests/users.http).

## Ограничения

- Колонка `users.phone` остаётся nullable: у записей, созданных до появления
  профиля, телефона нет. Ужесточение схемы — задача T-080.
- Своей отправки сообщений у сервиса нет и не будет: коды уходят через
  сервис оповещений, иначе пришлось бы дублировать очередь, повторы
  и ограничение частоты доставки.
