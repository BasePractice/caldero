# ADR 0004. Интеграция с маркетплейсами

**Статус:** принято
**Дата:** 2026-08-23

## Контекст

README требует интеграции с OZON и WB: из карточек товаров формируется
список желаний (FR-20), выбранный подарок заказывается (FR-24), шопоголик
оформляет случайный набор покупок (FR-50).

Проблема выяснилась до написания кода и записана здесь, потому что она
меняет продуктовый сценарий, а не только реализацию: **публичные API обеих
площадок ориентированы на продавца, а не на покупателя**. Продавец получает
доступ к своим товарам, заказам и остаткам. Оформление заказа от имени
произвольного покупателя в публичном API не предусмотрено.

Проверить это до конца, не имея доступа к кабинетам продавца, нельзя —
поэтому решение принимается так, чтобы отсутствие доступа не блокировало
всё остальное.

## Решение

Разделить интеграцию на две части и реализовать сейчас только первую.

**Часть 1, реализована.** Контракт `marketplace.Catalog`, кэширование,
размыкатель цепи и заглушка `Stub` для локальной разработки.

- Интерфейс объявлен у потребителя (`services/shared/marketplace`),
  а не рядом с реализацией.
- Метод `Order` может вернуть `ErrUnsupported`: это не заглушка «на потом»,
  а отражение того, что оформление заказа доступно не на всякой площадке.
- Кэш обязателен: у публичных API есть ограничения частоты, и обращаться
  к площадке на каждый показ списка желаний нельзя.
- Размыкатель цепи размыкается только на `ErrUnavailable`. Отсутствие товара
  ошибкой зависимости не считается — иначе цепь размыкалась бы от обычных
  запросов несуществующих товаров.
- Заглушка детерминирована: один идентификатор всегда даёт одну цену,
  иначе тесты становятся невоспроизводимыми.

**Часть 2, отложена.** Адаптеры OZON и WB. Начинать их нужно не с кода,
а с ответа на вопрос, что именно доступно стороннему приложению.

## Последствия

- Список желаний и шопоголик разрабатываются, не дожидаясь доступа к API:
  заглушка даёт карточки и цены.
- Продуктовый сценарий «выбранный подарок заказывается автоматически»
  может оказаться невыполнимым. Запасной вариант — ссылка на товар
  и ручной заказ дарителем; его стоит заложить в интерфейс списка желаний
  заранее, а не переделывать после.
- Цена в карточке снабжена отметкой времени: цена на площадке меняется,
  а котёл рассчитан на ту, что была при добавлении. Расхождение нужно
  показывать, а не молча пересчитывать.

## Альтернативы

- **Парсинг витрины вместо API.** Отвергнуто: нарушает условия использования
  площадок, ломается при любом изменении вёрстки и не даёт надёжных цен.
- **Партнёрские программы.** Дают ссылки и, возможно, карточки, но не
  оформление заказа. Стоит рассмотреть в части 2 как основной вариант.
- **Отказ от интеграции.** Список желаний свёлся бы к произвольному тексту
  и сумме. Это рабочий минимум, и если доступа к API не будет, продукт
  придётся строить именно так.

## Условия пересмотра

Появление доступа к API любой из площадок либо подтверждение, что
оформление заказа от имени покупателя недоступно в принципе — во втором
случае переписывается требование FR-24, а не код.
