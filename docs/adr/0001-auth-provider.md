# ADR 0001. Провайдер аутентификации: Keycloak и собственный, с переключением

**Статус:** принято
**Дата:** 2026-08-23

## Контекст

В системе одновременно существовали две реализации одной задачи:

- Keycloak — поднят в `docker-compose.yml`, realm `krakend` импортируется,
  шлюз настроен на его JWKS. `README.md` прямо пишет: «Лучше использовать
  Keycloak».
- Собственный OAuth2-провайдер на `ory/fosite` в `services/cmd/users` —
  со своим управлением RSA-ключами, хранилищем токенов и эндпоинтом JWKS.

Дублирование удваивает поверхность атаки и стоимость сопровождения в самой
дорогой для ошибок области. При этом у каждого варианта своя ценность:
Keycloak закрывает вход через соцсети и ЕСИА настройкой, а не кодом;
собственный провайдер — это учебная цель проекта.

## Решение

Оставить обе реализации и выбирать провайдера переменной окружения
`AUTH_PROVIDER` (`keycloak` или `internal`).

Точка переключения одна — какой JWKS считает доверенным API Gateway.
Сервисы за шлюзом ничего об этом не знают: они получают уже проверенный
идентификатор в заголовке `X-Authorized-Id`.

Технически:

- `config/krakend/krakend.tmpl` использует `{{ env "AUTH_JWKS_URL" }}`
  и подобные подстановки, KrakenD запускается с `FC_ENABLE=1`.
  Один конфиг вместо двух копий, расходящихся при первом же изменении.
- Keycloak вынесен в профиль compose `keycloak`: в режиме `internal`
  контейнер не нужен.
- `.env.example` содержит оба готовых набора значений.

## Последствия

Собственный провайдер пришлось довести до работоспособности, иначе
переключатель был бы декоративным:

- `auth/validator` шлюза проверяет **RS256 JWT** по JWKS, а `CoreStrategy`
  была настроена как HMAC и выдавала непрозрачную строку, которую шлюз
  проверить не может. Access-токен теперь подписывается RS256.
- В заголовок токена кладётся `kid`: без него проверяющая сторона не знает,
  каким ключом из набора проверять подпись.
- Клиент заявлял grant `password`, но фабрика
  `OAuth2ResourceOwnerPasswordCredentialsFactory` не была зарегистрирована —
  эндпоинт `/token` не поддерживал ни одного гранта, кроме `refresh_token`.
  Фабрика зарегистрирована, в хранилище добавлен `Authenticate`.

Что остаётся платой за это решение:

- Две кодовые базы аутентификации вместо одной. Уязвимость в собственном
  провайдере остаётся уязвимостью, даже когда система работает на Keycloak.
- Приватные ключи подписи по-прежнему лежат в БД незашифрованными
  (относится только к режиму `internal`).
- Authorization Code Flow в собственном провайдере не реализован (T-061),
  поэтому режим `internal` поддерживает только `password` и `refresh_token`.
- Роли для T-064 в двух режимах приходят из разных источников: в Keycloak
  это `realm_access.roles`, в собственном провайдере такого понятия пока нет.

## Альтернативы

- **Только Keycloak.** Дешевле в сопровождении, закрывает T-051 настройкой.
  Отвергнуто: удаляет учебную часть проекта.
- **Только fosite.** Максимум учебной ценности. Отвергнуто: требует
  самостоятельно реализовать Authorization Code Flow с PKCE, страницу
  согласия и защиту ключей — и всё это в области, где ошибки дороги.
