# ADR 0009. Обратный прокси и TLS: Caddy перед стеком

**Статус:** принято
**Дата:** 2026-08-24

## Контекст

Стек окружения открывал наружу два порта по HTTP: шлюз с API и сервис
статики с интерфейсом. По этому каналу ходят пароли при входе, коды
подтверждения и токены доступа — то есть всё, ради чего систему стали бы
атаковать. [ADR 0008](0008-delivery.md) прямо назвал это условием, при
котором окружение годится для staging, но не для боя.

Сам шлюз KrakenD терминировать TLS умеет, но тогда сертификат нужно
получать и продлевать чем-то ещё, а интерфейс остаётся на отдельном порту
и отдельной схеме: страница по HTTP, запросы к API по HTTPS. Браузер такую
смесь либо блокирует, либо портит поведением по умолчанию — и правильно
делает.

Продление сертификата — не разовая настройка. Сертификат Let's Encrypt
живёт три месяца, и забытое продление выглядит как полный отказ системы
в случайный день через квартал после выката.

## Решение

**Caddy перед стеком, единственная дверь снаружи.**

Прокси публикует 80 и 443, всё остальное — база, кэш, шлюз, интерфейс —
уходит внутрь сети и наружу не смотрит вовсе. Разбор адресов простой:
`/api/*` идёт на шлюз, всё прочее — на статику. Оба адреса теперь один
и тот же, и вопрос «страница по одной схеме, API по другой» исчезает.

Caddy выбран за то, что снимает именно ту работу, которая иначе
забывается: он получает сертификат при первом обращении и продлевает его
сам, без cron, без отдельного клиента ACME и без второго конфигурационного
файла. Для `localhost` и внутренних имён он выпускает сертификат своим
удостоверяющим центром — поэтому тот же файл конфигурации годится
для проверки на машине разработчика, а не только на сервере.

Заголовки безопасности (`Strict-Transport-Security`, `X-Content-Type-Options`,
`X-Frame-Options`, `Referrer-Policy`) задаются в одном месте — на входе,
а не в каждом сервисе. Там же снимаются заголовки с версиями сервера
и шлюза: снаружи они нужны только тому, кто подбирает под них уязвимость.

## Последствия

Чем платим:

- **Ещё один контейнер в стеке** и ещё один файл конфигурации. Разбор
  Caddyfile проверяется дважды: `make deploy-check` и сам выкат — до того,
  как подменит образы. Ошибка в нём иначе выглядит как отказ всей системы
  разом, ведь это единственная дверь.
- **Тома с сертификатами.** Их нельзя терять между выкатами: Let's Encrypt
  ограничивает частоту выпуска, и стек, просящий новый сертификат при
  каждом перезапуске, упрётся в предел и останется без него.
- **Два окружения на одной машине уживаются хуже.** Порты прокси
  параметризованы, но проверка HTTP-01 требует именно 80-го, поэтому
  второму окружению нужен либо свой адрес на том же прокси, либо
  проверка по DNS-01.
- **Внутренний трафик по-прежнему открыт.** Прокси закрывает внешнюю
  половину NFR-10: браузер — стек. Между шлюзом и сервисами, между
  сервисами и базой TLS нет, и это отдельные задачи (T-047, T-049).
  Называть требование выполненным нельзя.
- **HSTS на год** — обещание, которое нельзя отозвать быстро: браузер,
  однажды его увидевший, откажется ходить по HTTP к этому имени.
  Для домена, который заводится под систему, это правильно; для чужого
  домена с другими сервисами на поддоменах `includeSubDomains` был бы
  ошибкой.

## Альтернативы

**nginx с certbot.** Привычнее и гибче в разборе адресов. Отвергнут:
продление живёт отдельно от прокси — в cron или systemd-таймере, — и его
отказ ничем не виден до того дня, когда сертификат протух. Здесь важнее
не гибкость, а то, чтобы забыть было нельзя.

**Traefik.** Тоже умеет ACME сам и хорошо живёт с docker. Отвергнут:
его сила — в динамическом обнаружении контейнеров по меткам, а состав
стека здесь фиксирован и описан одним файлом. Платить конфигурацией
за динамику, которой нет, незачем.

**TLS в самом KrakenD.** Убрал бы контейнер, но оставил бы сертификат
без автоматического продления и интерфейс — на отдельной схеме.

**Оставить HTTP и терминировать TLS на чужом прокси** (облачный
балансировщик, Cloudflare). Разумно там, где такой прокси уже есть;
здесь его нет, а заводить внешнюю зависимость ради одного сертификата —
менять одну работу на другую.

## Условия пересмотра

- появился внешний балансировщик, который и так терминирует TLS, — тогда
  прокси в стеке лишний;
- сервисов стало больше и состав перестал быть фиксированным — тогда
  обнаружение по меткам, то есть Traefik;
- понадобился mTLS внутри сети (T-049) — тогда решение о внешнем прокси
  не меняется, но перестаёт быть достаточным.
