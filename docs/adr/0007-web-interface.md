# ADR 0007. Веб-интерфейс на Go WebAssembly

**Статус:** принято
**Дата:** 2026-08-23

## Контекст

У системы не было интерфейса вообще: проверить список желаний, котёл или
профиль можно было только через `curl` и коллекции в `_requests`. Требование
FR-55 закрывается любым фронтендом, поэтому вопрос стоял не «нужен ли
интерфейс», а «на чём».

Учебная цель №1 из README — писать на Go. Отдельный фронтенд на JS или
TypeScript даёт вторую кодовую базу со своим сборщиком, своим набором
зависимостей и своими копиями моделей, которые расходятся с серверными
молча — до первой ошибки в браузере.

## Решение

**Интерфейс на Go, собранный в WebAssembly, без фреймворка.**

- Модели общие с сервисами: типы `wishlist.Item`, `notify.Message`,
  `credit.Amount` — те же самые, что сервер отдаёт в JSON. Расхождение
  клиента и сервера ловит компилятор, а не пользователь.
- Работа с DOM — напрямую через `syscall/js`. Фреймворки (`go-app`, `vugu`,
  `vecty`) принесли бы собственный жизненный цикл, свою сборку и зависимость,
  которую нужно сопровождать, — ради четырёх экранов это не окупается.
- Разметка собирается строками и обязательно проходит через
  `html.EscapeString`: подставлять ответ сервера в разметку как есть —
  это межсайтовый скриптинг, даже если сервер свой.

**Общие пакеты пришлось развязать с инфраструктурой.** Проверка показала
то, о чём предупреждал план: `shared/wishlist` тянул `shared/marketplace`,
а тот — инфраструктурный `services` с драйвером PostgreSQL, gRPC
и протобуфом. Бандл выходил **28 МБ** вместо **5 МБ**. Кэш и размыкатель
цепи вынесены в подпакет `marketplace/cached`, и модель товара снова
зависит только от `credit`.

**Вход — Authorization Code Flow с PKCE.** Интерфейс зарегистрирован как
публичный клиент без секрета: браузерное приложение не может его сохранить,
и притворяться, что может, значит выдавать перехваченный код за
доказательство подлинности. Клиент без секрета теперь распознаётся
сервисом пользователей как публичный, а для таких клиентов PKCE обязателен.

**Токен доступа живёт только в памяти вкладки.** В `localStorage` его читает
любой скрипт на странице; в `sessionStorage` попадает лишь проверочный код
PKCE, переживающий ровно один редирект. Цена решения — перезагрузка страницы
требует повторного входа.

**Раздача статики — отдельный маленький сервис `web`** с `embed`. Статика
не подмешивается к API-сервисам, а nginx не заводится: сервис на Go делает
то же самое, не добавляя в стенд ещё одну технологию. Адрес API отдаётся
браузеру отдельным ответом `config.json`, а не зашивается в бандл — один
и тот же файл должен работать и на стенде, и в бою.

## Последствия

- Бандл 12 МБ, около 3 МБ в gzip. Это дорого по меркам веба: типичный
  JS-интерфейс такого объёма укладывается в сотни килобайт. Плата принята
  осознанно — взамен получены общие модели и один язык.
- Первого показа страницы до загрузки бандла нет: серверного рендеринга
  WebAssembly не даёт. Для внутреннего интерфейса это приемлемо,
  для публичной посадочной страницы — нет.
- `tinygo` уменьшил бы бандл в разы, но усложняет сборку и ограничивает
  рефлексию, на которой держится `encoding/json`. Проверка отложена
  отдельной задачей, а не сделана «на всякий случай».
- WebSocket в интерфейсе не используется: KrakenD Community Edition его
  не проксирует (EXT-05), и лента оповещений читается длинным опросом.
- Кошелёк в интерфейсе не показывается: он доступен только по gRPC,
  а шлюз Community Edition gRPC тоже не проксирует (EXT-04).
- Сервис `web` — единственный, чей порт публикуется наружу. Это и есть
  точка входа браузера; API остаётся за шлюзом.

## Альтернативы

- **Отдельный фронтенд на JS/TypeScript.** Быстрее и легче по весу, но даёт
  вторую кодовую базу и собственные копии моделей. Для учебной цели «писать
  на Go» — прямой проигрыш.
- **Фреймворк на Go (go-app, vugu, vecty).** Ускорил бы разработку сложного
  интерфейса, но на четырёх экранах его собственная сложность превышает
  выигрыш, а зависимость пришлось бы сопровождать.
- **Серверный рендеринг на `html/template`.** Дал бы мгновенный первый показ
  и нулевой бандл, но привязал бы интерфейс к сервису пользователей и
  не позволил бы переиспользовать модели остальных сервисов на клиенте.

## Условия пересмотра

Размер бандла становится проблемой (медленные сети, мобильные клиенты) —
тогда проверяется `tinygo`, а при его неуспехе рассматривается отдельный
фронтенд. Появление публичных страниц, которым нужен серверный рендеринг
и индексация, тоже отменяет это решение для них.
